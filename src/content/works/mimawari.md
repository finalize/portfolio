作ったものが増えると、1つずつ見に行かなくなる。`mimawari` は5つのリポジトリを横断して叩き、いま手を動かすべきことだけを1画面にまとめて出すコマンド。毎朝これを1回打てばいい。

## きっかけは4日間の見落とし

[termpic](/works/termpic/) の Dependabot の PR が、4日間まったく気づかれずに止まっていた。リポジトリが1つなら毎日開くから気づく。4つになると開かなくなる。これから増えるほど、見に行かないと分からない状態は当たり前に取りこぼされる。

## `gh pr list` では足りなかった

止まっている PR を調べると `mergeStateStatus: BLOCKED` としか出てこない。これでは**承認ボタンを押せば動くのか、CI が落ちていて直すところがあるのか**が分からない。どちらも「blocked」だが、やることは正反対になる。

そこで `mergeable_state` だけでなく、チェックの内訳とワークフローの実行状態まで見て、止まっている理由を1つに分類することにした。判定は上から順に確かめて、先に当たったものが勝つ。直し方が違うものほど先に置いてある。

| 状態 | やること |
|---|---|
| 承認待ち | 承認ボタンを押す |
| 競合 | 手元で解消する |
| チェックが落ちている | 落ちたチェックを直す |
| base に遅れている | 更新する |
| チェック待ち | 待つ（長引いたときだけ知らせる） |
| 説明の付かない blocked | 必須チェックが始まっていないか、レビューが足りない |

**落ちたチェックの名前まで出す。** 「1件落ちている」で止めると、結局リポジトリを開くことになって見回りの意味が半分無くなる。実際に動かしたら、4日止まっていた PR は承認待ちではなく `check & test & build` が落ちているのだと一発で分かった。

PR のほかに、npm に公開したバージョンと手元の `package.json` のずれ、公開しているサイトが返事をするか、動かなくなった issue も見る。

## Go にした理由

これまでの4つは全部 TypeScript だったので、違う言語を実地で覚えたかった。題材のほうが後から決まった。

そのうえで、この題材は Go に向いていた。1回の見回りで 30 回ほど問い合わせるが、プロジェクトごとに goroutine を立て、その中で GitHub・npm・サイトをさらに並列に、PR は1件ずつさらに並列に取る。全体で 1.2 秒。直列に並べたら6〜10秒かかる計算になる。`go` の1語で書けるので、並列にすることに構えが要らないのがよかった。

外部の依存はゼロ。標準ライブラリだけで書いてある。テストも実際のネットワークには出さず、GitHub も npm もサイトも全部 `httptest` の偽サーバに差し替えている。

## API として作って、CLI に作り替えた

最初は `/status` を返す HTTP サーバとして書いた。動くようにしてから使ってみたら、叩くのは1日1回で、キャッシュもエンドポイントの出し分けも何も効いていなかった。しかもサーバを1つ持つと、置き場所という宿題まで付いてくる。ほかの4つと違って Cloudflare Workers は Go を動かせないので、そこだけ構成が揃わない。

そこでサーバとキャッシュを消して、ただのコマンドにした。**削ったのは2つのパッケージだけで、中身には一切触っていない。** 集める処理が HTTP を知らないように書いてあったから、外側の形だけ選び直せた。置き場所の問題もそのまま消えた。

「まず作って、使ってから決める」がそのまま効いた例だった。設計として正しかったのは、サーバにしたことではなく、**あとで捨てられる形にしておいたこと**のほうだった。
