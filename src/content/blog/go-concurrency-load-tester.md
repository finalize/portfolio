Go で [mimawari](https://github.com/finalize/mimawari) を書いたとき、並行処理は `sync.WaitGroup` と `sync.Mutex` で「並行に投げて全部待つ」までしか使わなかった。チャネルで値を集める・`select` で分ける・本数を絞る・途中で畳む、が丸ごと空いたままだった。そこを埋めるための題材として、HTTP を連打して捌ける量と遅延を測るツールを作った。[renda](https://github.com/finalize/renda) という名前で、撃つ先の的サーバを同梱しているので手元で完結する。

## 3層に分ける

撃つ側の構造はこれだけ。

```
配る goroutine 1本 ──jobs──▶ ワーカ -c 本 ──results──▶ 集計 goroutine 1本
```

```go
// 集計はこの1本だけ。sum を触るのがここに閉じているのでロックが要らない。
go func() {
	defer close(done)
	for r := range results {
		sum.Add(r)
	}
}()

var wg sync.WaitGroup
for range o.Concurrency {
	wg.Add(1)
	go func() {
		defer wg.Done()
		for {
			select {
			case _, ok := <-jobs:
				if !ok {
					return
				}
				results <- Do(ctx, client, o.URL, o.Timeout)
			case <-ctx.Done():
				return
			}
		}
	}()
}

wg.Wait()      // 送り手が全員終わった。
close(results) // ので、ここで初めて閉じてよい。
<-done         // 集計が残りを食べ終わるまで待つ。
```

値が2本のチャネルを一方向に流れるだけで、複数の goroutine が同じ変数を書く場所が1つもない。だから集計を持つ構造体にロックが付いていない。mimawari では逆に `sync.Mutex` で共有変数を守る側の書き方をしていて、どちらも正しい。状態の置き場所が違うだけだった。

## 壊れるのはいつも順番

書いてみて実際に踏んだのは3つで、どれも処理の中身ではなく順番の間違いだった。

- **`close(results)` を配る側でやった。** results に送るのはワーカなので、送り手が生きているうちに閉じると次の送信で `send on closed channel` になる。閉じてよいのは「送り手が全員終わった」と知っている者だけで、それは `wg.Wait()` の後の本体しかいない
- **集計の `for r := range results` を `go func` で包み忘れた。** 本体がそこで止まり、ワーカを立てる行に到達しない。誰も送らないので永久に待つ
- **キャンセル時の `return` で `close(jobs)` を飛ばした。** jobs が閉じられないのでワーカが待ち続け、`wg.Wait()` が返らなくなる。`defer close(jobs)` にするだけで直る

3つとも「誰がこのチャネルを閉じるのか」「誰がこの終わりを待つのか」を決めていれば起きない。書く前にそこだけ決めておけばよかった。

## 速くなった理由を測る

50ms 待つ的に 500 本を同時 50 で撃つと 520ms で終わる。逐次なら 500 × 50ms で 25 秒かかる計算になる。

```
500本 ÷ 同時50本 = 10回
10回 × 50ms      = 500ms
実測              = 520ms
```

計算どおりで、種も仕掛けもない。**1本あたりの 50ms は最後まで 50ms のまま**で、縮んだのは合計だけ。並行化で良くなるのはさばける量であって、1本の速さではない。

## 並行と並列は別のもの

同じコードのまま `GOMAXPROCS` だけ変えて、sha256 を回すだけの（待ちがゼロの）仕事を14個投げるとこうなる。

| GOMAXPROCS | 逐次 | goroutine 14本 | 短縮 |
|---|---|---|---|
| 1 | 446ms | 433ms | 1.0倍 |
| 4 | 440ms | 123ms | 3.6倍 |
| 14 | 432ms | 39ms | 11.1倍 |

1行目が「並行だが並列ではない」状態で、goroutine は14本ちゃんと動いているのに1つも速くなっていない。速くしたのは goroutine ではなくコアだった。

ところが renda のほうは、5ms 待つ的に 2000 本を同時 50 で撃っても `GOMAXPROCS=1` で 8,121 req/s、既定（14）で 8,516 req/s。**1コアでも95%出る**。待っている間 CPU は何もしていないので、同時に待つのにコアは要らない。

## どちらで速くなったかは CPU 時間でわかる

`/usr/bin/time -p` で実時間と CPU 時間を比べると一目でつく。

| | 実時間 | CPU 時間 |
|---|---|---|
| sha256（GOMAXPROCS=14） | 0.47s | 0.89s |
| renda（50ms 待つ的に500本） | 0.52s | 0.05s |

上は CPU 時間が実時間を超えている。1つの時計に対して CPU が2つぶん働いた、つまり同時に走った証拠で、これが並列。下は逆に CPU 時間が実時間の1割しかなく、ほとんどの時間なにも走っていない。25秒ぶんの待ちを 0.52 秒に畳んだのは並列実行ではなく、待ちを重ねただけだとわかる。

「並列化したつもりが実は待ちを畳んでいただけ」も「コアを増やしたのに user が増えない」も、この比を見るだけで判別できる。

## 接続を使い回さないと接続を測ることになる

負荷試験ツールを書いていて一番効いたのはここだった。`http.DefaultClient` はホストあたりの idle 接続を2しか持たないので、同時50本で撃つと48本は毎回 TCP から張り直す。

実際に1本のリクエストの内訳を測るとこうなる。

```
DNS 解決        2.3ms
TCP 接続完了     18ms   ← 3ウェイハンドシェイク（1往復）
TLS 完了         45ms   ← 鍵の交換（1往復＋暗号計算）
最初の1バイト     82ms
全部完了         84ms
```

**84ms のうち 45ms、半分以上がまだ1バイトも運んでいない時間**で、同じ接続を使い回した2本目は 26ms で終わる。ここを直さないと、測っているのはサーバの速さではなくハンドシェイクの速さになる。

```go
tr := http.DefaultTransport.(*http.Transport).Clone()
tr.MaxIdleConns = concurrency
tr.MaxIdleConnsPerHost = concurrency
```

## まとめ

- **待つ仕事**は、同時に待てば終わる。コアは要らない
- **計算する仕事**は、コアの数ぶんしか速くならない

判断に使うのはこの2行で足りて、あとは `-race` を必ず付けることと、投げっぱなしの goroutine を作らないことを守っていれば、踏むバグの大半は避けられる。次はレート制限と、Ctrl-C で飛んでいる最中のリクエストを殺さずに畳むところを足す。
